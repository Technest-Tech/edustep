# الملخص التنفيذي لخطة تنفيذ EduStep Academy OS

## 1. النتيجة

الخطة أصبحت جاهزة لتحويل النظام إلى مشروع برمجي باستخدام:

- Laravel 13 وPHP 8.4 للـBackend.
- Next.js App Router وTypeScript للـFrontend.
- Node.js 24 LTS.
- PostgreSQL 18.
- Redis للـQueues والـCache والـLocks.
- Object Storage للملفات الخاصة.
- منصة Responsive وPWA بدل تطبيقات منفصلة في البداية.

لن نبدأ كـMicroservices. سنبني **Modular Monolith** منظمًا؛ كل جزء له
مسؤوليته، لكن التشغيل والنشر يظلان بسيطين.

---

## 2. شكل النظام

سيكون هناك ثلاث تجارب مختلفة فوق نفس النظام:

1. **مساحة الإدارة والموظفين:** المبيعات، القبول، التشغيل، الأكاديمي والمالية.
2. **مساحة المعلم:** جدول اليوم، الحضور، تقرير الحصة، التقييمات والمستحقات.
3. **مساحة الأسرة:** الأبناء، الجداول، الحضور، التقدم، الفواتير والطلبات.

الواجهة عربية RTL من البداية، وليست ترجمة لاحقة. التصميم يعتمد على هوية
EduStep الحالية: Navy وTeal وYellow، وخط Alexandria للعربية وManrope
للإنجليزية.

---

## 3. أهم القرارات الهندسية

- Laravel هو صاحب قواعد العمل والصلاحيات والبيانات.
- Next.js مسؤول عن تجربة الاستخدام والواجهات.
- التواصل بينهما عبر REST API موثق بـOpenAPI.
- Laravel Sanctum يدير تسجيل الدخول بجلسة Cookie آمنة.
- لا يتم تخزين JWT داخل `localStorage`.
- PostgreSQL هو مصدر الحقيقة الوحيد.
- الأموال تُخزن بالقروش كأرقام صحيحة، وليس Decimal عائم.
- التوقيت يُخزن UTC ويُعرض بتوقيت القاهرة.
- المعاملات المالية لا تُحذف؛ تُلغى أو تُعكس بحركة واضحة.
- كل تعديل حساس له Audit Log.
- تكاملات Meta وWhatsApp وPaymob تكون Adapters منفصلة عن قواعد النظام.
- رسائل وتكاملات النظام تعمل عبر Queues حتى لا تبطئ الواجهة.

## 4. البيانات الأساسية

تم الفصل بين الكيانات التالية حتى لا تظهر مشكلات مستقبلية:

- الأسرة وولي الأمر والطالب.
- Lead والطالب بعد التحويل.
- الطالب والجروب والاشتراك Enrollment.
- الجروب والحصص الفعلية.
- الحضور ورصيد الحصة التعويضية.
- السعر الحالي والسعر المطبق وقت الاشتراك.
- سعر المعلم ومستحقه المحسوب للحصة.
- الفاتورة والدفع وتخصيص الدفع.
- المنهج ونسخة المنهج المستخدمة في كل جروب.

هذا يسمح بالتعامل الصحيح مع:

- أكثر من ابن لنفس ولي الأمر.
- النقل بين الجروبات.
- التجميد.
- الحصص التعويضية.
- الدفع الجزئي.
- الاسترداد.
- تغير أسعار الباقات.
- تغير أسعار المعلمين.
- مدرس بديل.

---

## 5. تجربة الاستخدام

الفكرة الأساسية:

> هدوء وتحكم للإدارة، سرعة للمعلم، وتقدم واضح لولي الأمر.

أهم أهداف سهولة الاستخدام:

- المعلم يسجل حضور جروب عادي في أقل من دقيقة من الهاتف.
- مسؤول المبيعات يعرف فورًا من يحتاج متابعة.
- تقييم المستوى والحجز يتمان دون فتح تقويم خارجي.
- نقل الطالب يعرض أثر الجدول والمال والتنبيهات قبل التأكيد.
- المحاسب يستطيع تفسير أي رصيد من سجل الحركات.
- ولي الأمر يرى الحصة القادمة في أول شاشة.
- كل رقم في Dashboard يفتح القائمة التي أنتجته.

## 6. مراحل التنفيذ

الخطة مبنية على Sprints مدتها أسبوعان لفريق صغير متفرغ.

| المرحلة | الناتج |
|---|---|
| Sprint 0 | تثبيت السياسات، Wireframes، Prototype ونظام التصميم |
| Sprint 1 | المشروع، تسجيل الدخول، الصلاحيات، RTL، CI وStaging |
| Sprint 2 | CRM، Leads، المتابعات، الأسرة، الطالب والمعلم |
| Sprint 3 | تقييم المستوى، التجربة، العرض وتحويل الـLead |
| Sprint 4 | البرامج والمستويات والجروبات والجدول والحصص |
| Sprint 5 | مساحة المعلم، الحضور، تقرير الحصة ومستحق المعلم |
| Sprint 6 | الباقات، الفواتير، الأقساط، الدفع والتحصيل |
| Sprint 7 | التقدم الأكاديمي وبوابة الأسرة |
| Sprint 8 | الأمان، الاختبارات، الاستيراد، النسخ الاحتياطي والـPilot |

### متى يظهر نظام قابل للاستخدام؟

- بعد Sprint 2: CRM داخلي أولي.
- بعد Sprint 4: تشغيل الجروبات والجدول داخليًا.
- بعد Sprint 6: المسار الكامل من Lead إلى طالب مدفوع وحصة ومستحق معلم.
- بعد Sprint 8: إصدار Pilot جاهز لبيانات وتشغيل حقيقي محدود.

التوقيت يتغير حسب حجم الفريق وسرعة اعتماد سياسات الأكاديمية. مع مطور واحد
يبقى نفس الترتيب، لكن المدة تزيد.

## 8. الاختبارات والجودة

لن يعتمد النظام على الاختبار اليدوي فقط:

- Unit Tests لقواعد المال والتعويض ومستحق المعلم.
- Laravel Feature Tests للـAPI والصلاحيات والمعاملات.
- Contract Tests بين Laravel وNext.js.
- Component Tests للواجهات.
- Playwright للمسار الكامل.
- اختبارات عزل بيانات الفروع والمعلمين والأسر.
- اختبارات تكرار Webhooks والمدفوعات.
- Accessibility وRTL وموبايل.
- Performance واختبار آخر مقعد في الجروب.
- تجربة استرجاع Backup قبل الإطلاق.

## 9. القرارات المطلوبة قبل البرمجة

أهم ما يحتاج الاعتماد في Sprint 0:

1. هل الإطلاق Online أم Hybrid؟
2. ما البرامج والفئات العمرية الأولى؟
3. أسماء المستويات وربطها بـCEFR.
4. مراحل الـLead وزمن الرد المستهدف.
5. نموذج تقييم المستوى.
6. نوع الاشتراكات والأسعار والأقساط.
7. سياسة الغياب والتعويض.
8. سياسة التجميد والنقل والاسترداد.
9. طرق حساب مستحقات المعلمين.
10. أدوار الموظفين الفعلية.
11. الاستضافة والدومين.
12. ترتيب Meta وWhatsApp وPaymob.

الخطة وضعت Default آمنًا لكل قرار حتى لا يتوقف التصميم، لكن يجب اعتماده قبل
الـSprint المرتبط به.

---

## 10. الخطوة التنفيذية التالية

بعد اعتماد الـBlueprint:

1. تنفيذ Sprint 0.
2. إنتاج Wireframes وPrototype للمسار الذهبي.
3. اعتماد تصميم الواجهات.
4. إنشاء Laravel وNext.js والبيئة المحلية.
5. نشر أول Staging.
6. بدء Sprint 2 على CRM.

التنفيذ لا يبدأ بإنشاء عشرات الجداول والشاشات دفعة واحدة. يبدأ بمسار صغير
يعمل من الطرف للطرف، ثم يتوسع مع اختبارات وبيانات حقيقية.
